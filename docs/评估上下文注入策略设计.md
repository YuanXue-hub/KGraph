# 评估上下文注入策略设计

> 本文档记录 KGraph LLM-as-Judge 评估的上下文注入方案演进：从「全文注入」的问题出发，对比「局部窗口 ±150 字」与「全文注入」的优劣，重点解决双时态评估的跨段时间锚点关联问题，最终给出分指标差异化策略。
>
> 关联文档：[评估方法消融与对比实验设计](./评估方法消融与对比实验设计.md)（提示词锚点校准、计分公式、裁判模型对比）

***

## 一、背景与问题

### 1.1 当前实现

`pybackend/api/evaluation.py` 的 `_judge` 函数（L164）在每次裁判调用时，将**完整原文**塞入 prompt：

```python
user = (
    f"## 原文\n```\n{text}\n```\n\n"
    f"## 待评估样本\n{json.dumps(items, ensure_ascii=False)}\n\n"
    ...
)
```

5 个裁判指标共用同一函数，全部吃全文。

### 1.2 观察到的问题

| 问题 | 表现 | 来源 |
|---|---|---|
| **注意力稀释** | 长文（>3K 字）裁判注意力分散，同一样本两次评估 verdict 漂移 | 记忆：极差 0.1045 |
| **谓词指标方差最大** | 弱谓词（关联/提及）判定主观性强，裁判每次"看的地方不一样" | 记忆 + 消融实验数据（谓词极差 0.0228，忠实度 0.0151） |
| **Token 浪费** | 星海数科 3492 字，单指标 prompt ~41K token，5 指标合计 ~205K | 实测 |
| **裁判看了不该看的** | 忠实度指标需要的证据就在 ±150 字内，但裁判被远处无关段落干扰 | 消融实验观察 |

### 1.3 记忆中的局部窗口设计（未实现）

项目记忆已记录"局部上下文注入 + 固定种子抽样 + 小批量分批"的改进方向，局部窗口方案的记忆实测数据：

| 指标 | 全文注入极差 | 局部窗口极差 |
|---|---|---|
| 三元组忠实度 | ~0.10 | <0.03 |
| 谓词合理性 | 最大方差 | 待验证（预期改善显著） |
| 双时态正确性 | — | 有跨段锚点风险 |
| Token 消耗 | ~41K/指标 | ~15K/指标（省 63%） |

## 二、两种方案定义

| | 方案 A：全文注入（当前代码） | 方案 B：局部窗口 ±150 字（待实现） |
|---|---|---|
| 裁判可见原文 | 完整全文，塞在 prompt 公共参数里 | 每条样本围绕 evidenceSpan 中心 ±150 字切片，附在 item 内 |
| prompt 结构 | `## 原文\n{全文}\n## 样本\n{items}` | `## 样本\n[{item: {localContext, ...}}]` |
| 切片触发 | 无，总是全文 | 每条关系独立切片 |

## 三、逐指标对比

### 3.1 三元组忠实度

| | 方案 A 全文 | 方案 B 局部窗口 |
|---|---|---|
| 核心判断 | 关系是否被原文语义支持 | 同左 |
| 跨句合并 | ✅ 全文可见，裁判能合并跨句信息 | ✅ ±150 字通常覆盖跨句（中文段落 ~200-400 字） |
| 否定关系（"并无""否认"） | ✅ 全文能找到远处否定词 | ⚠️ 否定词可能在 ±150 外 → **需全文否定关键词预扫描补信号** |
| 方差 | 🟡 全文杂讯稀释注意力 | ✅ 窗口聚焦，注意力集中 |

**结论**：方案 B，需补否定关键词预扫描。

### 3.2 谓词合理性

| | 方案 A 全文 | 方案 B 局部窗口 |
|---|---|---|
| 核心判断 | 谓词是否恰当、方向是否正确 | 同左 |
| 远处更强谓词 | ✅ 全文可见，裁判能发现"附近有更好谓词却用了弱谓词" | 🟡 窗口内没有更好谓词就判"合理"，但远处可能有 → **误判率略高** |
| 方差 | 🔴 所有指标中方差最大（记忆） | ✅ 局部聚焦后方差应显著降低 |

**结论**：方案 B。远处更强谓词的代价是可接受的——"附近有更具体关系可用而用弱谓词"的场景（裁判判 1 而非 0），本身就是谓词合理性判定中最主观的部分，局部窗口让裁判聚焦证据句附近的关系密度，反而比全文乱看更稳定。

### 3.3 双时态正确性

| | 方案 A 全文 | 方案 B 局部窗口 |
|---|---|---|
| 核心判断 | vt_from / vt_to 是否符合原文语义 | 同左 |
| 跨段时间锚点 | ✅ 全文可见（"曾任"在段 1，"卸任"在段 3） | 🔴 ±150 字可能覆盖不到 → **这是核心难点** |
| 时间值精度 | ✅ 全文能比对多个日期的相对关系 | ⚠️ 窗口内只有一个日期时，裁判无法判断是否还有更早/更晚的 |
| 方差 | 🟡 中等（时间信号是硬字符串匹配，主观性低） | 取决于跨段锚点的补充方式 |

**结论**：暂保留方案 A，待跨段锚点方案落地后再迁移。详见第四章。

### 3.4 证据句有效性

| | 方案 A 全文 | 方案 B 局部窗口 |
|---|---|---|
| 核心判断 | evidenceSpans 切片是否支撑三元组 | 同左 |
| 证据定位 | 🟡 全文里找 evidenceText 切片验证 OK，但裁判被其他信息干扰 | ✅ 直接用 evidenceSpans 切片，任务清晰 |
| 方差 | 🟡 中等 | ✅ 窗口中心就是证据句，最稳定 |

**结论**：方案 B。

### 3.5 实体边界正确性

| | 方案 A 全文 | 方案 B 局部窗口 |
|---|---|---|
| 核心判断 | 实体名称是否完整、类型是否匹配 | 同左 |
| 截断检查 | ✅ 全文能看实体名前后有没有被截断 | ✅ ±150 字足够覆盖实体名的完整上下文 |
| 方差 | 🟡 中等 | ✅ 稳定 |

**结论**：方案 B。

## 四、双时态跨段锚点问题（核心难点）

### 4.1 问题

局部窗口 ±150 字后，以下场景的时间锚点不在窗口内：

```
段 1："陈志远曾任国开行高管"          ← "曾任"（PREVIOUS 信号）
...（300 字）...
段 3："2024 年 6 月，陈志远正式卸任"   ← 证据句在此，±150 窗口覆盖不到段 1
```

裁判只看窗口 → 看不到段 1 的"曾任" → 可能误判 vt_to=2024-06 为 0 分（"窗口里只看到卸任，没看到曾任"）。但原文跨段明确有终止信号，应该判 2。

### 4.2 纯代码扫描的硬伤

**代码只能做精确字符串匹配，做不了语义关联**。扫描产出：
- 绝对日期：2018（段1）、2024-06（段2）
- PREVIOUS 信号：曾任（段3）

代码无法判断 "2024-06 到底是董事会换届的时间，还是陈志远离任的时间"——它可能和两者都没关系（离任日期原文根本没写）。

### 4.3 三条解决方案路线

#### 路线 1：代码只产孤立信号，裁判自己做关联

扫描只产出"全文有哪些日期、哪些 OPEN/PREVIOUS 关键词"的**索引**，不做关联。裁判结合局部窗口 + 索引自己判断。

```
裁判样本：
  局部窗口："...陈志远曾任国开行高管..."
  temporalSummary：
    - 全文日期：2018(字符120)、2024-06(字符1832)
    - 全文 PREVIOUS 信号：曾任(字符2450)、已卸任(字符4100)
```

| 优点 | 缺点 |
|---|---|
| 零 LLM 额外调用，改动最小 | 裁判需要在"局部窗口 + 一堆远程信号"之间做跨段推理 → **注意力又开始分散**，等于把全文注入的问题换了个形式搬回来 |

**不推荐**。

#### 路线 2：复用抽取阶段的 timeAnchors（推荐）

抽取阶段的 LLM **已经从全文视角抽好了带语义的 timeAnchors**：

```json
{
  "expr": "2024年6月",
  "type": "DATERANGE",
  "normISO": "2024-06",
  "precision": "month",
  "start": 1832
}
```

关键：这些 timeAnchors 是 LLM 做过语义关联的产物——它知道「2024年6月」是和「卸任」连在一起的，而不是和「董事会换届」连在一起的。

**评估时做法**：
1. 直接拿抽取结果里的 `timeAnchors`（不需要重新扫描）
2. 对每条关系，按 evidenceSpan 的位置找 **proximity 最近的 timeAnchors**（代码做距离排序，不做语义判断）
3. 把最近的 1-3 个 timeAnchors 附加到裁判样本里

```
裁判样本：
  局部窗口："...2024年6月，陈志远卸任..."
  nearbyTimeAnchors（按离 evidenceSpan 距离排序）：
    1. {expr:"2024年6月", normISO:"2024-06", type:"DATERANGE", start:1832, 距证据句:42字}
    2. {expr:"曾任", type:"PREVIOUS_KEYWORD", start:2450, 距证据句:660字}
```

裁判结合局部窗口 + 附近 timeAnchors 做判定。**代码只做 proximity 排序，语义关联权交给裁判**——但 timeAnchors 的 type（ABSOLUTE vs PREVIOUS vs OPEN）已经给了裁判强信号。

| 优点 | 缺点 |
|---|---|
| 复用已有产物、零额外 LLM 调用 | timeAnchors 和关系也没有显式绑定，proximity 可能误关联（两个事件靠得近时） |
| timeAnchors 自带 LLM 语义关联 | |

**推荐**。proximity 误关联的代价低——裁判看了 timeAnchors 的 type 后会自然过滤（比如「董事会换届」的时间锚点 type=ABSOLUTE，不是 PREVIOUS，裁判知道它和"曾任"没关系）。

#### 路线 3：双时态保留全文，其余 4 指标改局部（务实取舍）

记忆里的教训：**谓词合理性是所有指标中方差最大的**（弱谓词判断主观性强），而双时态的方差其实没那么大——因为时间信号是硬字符串匹配（"曾任"要么在要么不在），裁判不需要太多"左右看"。

针对性取舍：

| 指标 | 上下文策略 | 理由 |
|---|---|---|
| 三元组忠实度 | 局部 ±150 + 全文否定关键词预扫描 | 跨句合并在 ±150 内足够，否定词代码扫 |
| 谓词合理性 | 局部 ±150 | 方差最大的指标，局部聚焦收益最大 |
| **双时态正确性** | **全文** | 跨段时间锚点关联是硬需求，且方差本身不大 |
| 证据句有效性 | 局部 ±150 | 证据句就在窗口中心 |
| 实体边界正确性 | 局部 ±150 | 实体名完整上下文足够 |

| 优点 | 缺点 |
|---|---|
| 精准打击方差最大的指标，双时态不丢跨段信号 | 双时态仍吃全文 token（~8K 字 / 指标），但只占 1/5 指标 |
| 总 token 仍省 ~50% | |

### 4.4 推荐方案：路线 2 + 路线 3 混合

1. **先做 4 个指标改局部窗口**（忠实度、谓词、证据、实体边界）——成本最低、收益确定
2. **忠实度加全文否定关键词预扫描**（代码扫，0 LLM）
3. **双时态暂时保留全文**——方差不大，不急着改
4. **同时实现路线 2 的 timeAnchors 复用**——为双时态后续迁移铺路
5. 观察数据：如果双时态方差确实小（<0.03），就保留全文；如果方差也大，再尝试把窗口扩大到 ±400 试

### 5.2 实现细节

#### 5.2.1 localContext 切片

```python
def _slice_window(text: str, center: int, radius: int = 150) -> str:
    """以 center 为中心，左右各 radius 字切片，边界夹紧。"""
    start = max(0, center - radius)
    end = min(len(text), center + radius)
    return text[start:end]
```

center 取 `evidenceSpans[0].start`（第一条证据句的起始位置）。

#### 5.2.2 全文否定关键词预扫描（忠实度指标用）

```python
NEGATIVE_KEYWORDS = ["并无", "否认", "未发生", "并未", "不存在", "予以否认", "传闻不实", "不实"]

def _scan_negatives(text: str) -> List[Dict]:
    """全文扫描否定关键词，返回 [{keyword, start, end, expr}]。"""
    results = []
    for kw in NEGATIVE_KEYWORDS:
        idx = 0
        while True:
            pos = text.find(kw, idx)
            if pos < 0:
                break
            results.append({
                "keyword": kw,
                "start": pos,
                "end": pos + len(kw),
                "expr": text[max(0, pos-10):min(len(text), pos+len(kw)+10)]
            })
            idx = pos + 1
    return results
```

忠实度裁判 prompt 追加：
```
## 全文否定信号（代码预扫描，仅供裁判参考）
- 全文发现 N 处否定表述：「并无」(字符123)、「否认」(字符456)...
- 若局部窗口未出现否定词但全文有，裁判需判断该否定词是否指向本三元组
```

#### 5.2.3 全文时间预扫描（双时态后续迁移用）

ABSOLUTE_DATE_PATTERNS = [

#### 5.2.4 复用抽取阶段 timeAnchors（路线 2）

```python
def _nearby_time_anchors(anchors: List[Dict], center: int, limit: int = 3) -> List[Dict]:
    """按离 center 的距离排序，取最近的 limit 个 timeAnchors。"""
    enriched = []
    for a in anchors:
        start = a.get("start") or 0
        enriched.append({**a, "distance": abs(start - center)})
    enriched.sort(key=lambda x: x["distance"])
    return enriched[:limit]
```

#### 5.2.5 _judge 函数 prompt 改造

当前（全文注入）：
```python
user = (
    f"## 原文\n```\n{text}\n```\n\n"
    f"## 待评估样本\n{json.dumps(items, ensure_ascii=False)}\n\n"

```

改造后（局部注入）：
```python
user = (
    f"## 待评估样本（每条样本附局部原文 ±150 字）\n"
    f"{json.dumps(items, ensure_ascii=False)}\n\n"
    ...
)
```

items 结构：
```json
{
  "id": 1,
  "head": "陈志远",
  "predicate": "曾任",
  "tail": "国开行高管",
  "localContext": "...±150字窗口文本...",
  "negativeSummary": "## 全文否定信号\n- 无",

}
```

裁判 prompt 里的评估标准（criteria）需要微调——把"基于原文判定"改为"基于局部原文判定，否定/时间等全局信号参考附加摘要"。

### 5.3 降级兜底

| 场景 | 处置 |
|---|---|
| evidenceSpans 缺失或无效 | fallback 全文注入（单条样本级降级，不影响其他） |
| 全文扫描没找到任何否定/时间信号 | 摘要为空 → 裁判退化为只看局部窗口 |
| timeAnchors 为空（抽取阶段没抽时间锚点） | 不附加 nearbyTimeAnchors，不影响判定 |

### 5.4 验证用例

1. **窗口正确性**：evidenceSpan 切片 + ±150 字窗口，切片 == evidenceText 原文
2. **跨句覆盖**：关系 evidenceText 跨两句，±150 窗口应覆盖
3. **否定词跨段**：否定词在 ±150 外，全文扫描应能发现并附加到摘要
4. **双时态跨段**：曾任（段1）+ 卸任（段3），timeAnchors proximity 排序应关联
5. **Token 对比**：同一评估，改造前后总 token 差应接近 63%
6. **方差对比**：同一抽取结果跑 3 次，改造后极差应 < 0.03（忠实度/谓词/证据/实体）

## 六、风险与权衡

| 风险 | 影响 | 控制措施 |
|---|---|---|
| evidenceSpans 漂移 | 切片中心错位 → 局部窗口上下文不完整 | 抽取阶段 span 由代码 `find()` 定位（非 LLM 偏移），可靠性有保障；窗口切片前先 `find(evidenceText)` 二次校准 |
| 局部窗口裁剪 | 边界处的否定/时间信号被切掉 | 扩大窗口到 ±200 试；或窗口重叠 50 字 |
| 裁判无法看远处 | 确实需要全文才能判定的样本（如跨 3 段的复杂关系）可能误判 | 双时态暂保留全文作为兜底；观察误判率后决定是否扩大特定指标窗口 |
| timeAnchors proximity 误关联 | 两个事件靠得近时，时间锚点可能关联到错误的关系 | proximity 只给裁判参考，type 字段（ABSOLUTE vs PREVIOUS vs OPEN）提供强语义信号，裁判会自然过滤 |
