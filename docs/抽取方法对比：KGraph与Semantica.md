# 抽取方法对比：KGraph vs Semantica

> 对比对象：
>
> * **KGraph**：`pybackend/api/extraction.py` + `pybackend/core/prompt_builder.py` + `pybackend/core/extraction_validator.py`（Semantica 式两阶段流水线，2026-08-23 重构）
>
> * **Semantica**：`semantica/semantic_extract/` 模块（`methods.py` 约 2600 行），源码分析见 [Semantica抽取机制源码分析.md](file:///Users/Yuan/xy_workspace/2.projects/java/KGraph/docs/Semantica抽取机制源码分析.md)
>
> 评估数据来源：抽取任务 `2094406639339233282`（诉讼001 语料，45 关系 + 23 实体）的历史评估记录。

***

## 一、总体架构对比

| 环节    | Semantica                                                                     | KGraph                                       | 评价                                                                         |
| ----- | ----------------------------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------- |
| 抽取范式  | 两阶段（NER → 关系），多方法 fallback 链（pattern/regex/rules/ml/huggingface/llm）          | 两阶段（节点 → 关系），纯 LLM                           | KGraph 借鉴了其两阶段骨架；Semantica 的多方法 fallback 适合无 LLM 场景，KGraph 定位 LLM 抽取，单方法合理 |
| 长文本切分 | **内置**：超 64K 字符自动分块 + 10% overlap + `ThreadPoolExecutor` 并发 + chunk 偏移回加 span | **无**（`corpus_chunk` 表已预留，切分逻辑未集成）           | KGraph 待补的核心工程环                                                            |
| 抽取后处理 | 独立 `deduplication/` + `normalize/` 模块                                         | W3 仅做别名替换式消歧，无独立去重模块                         | KGraph 待补                                                                  |
| 图存储   | graph\_store / triplet\_store，通用                                              | Neo4j + `modelId` 多模型隔离 + 关系不 merge（保留时态多版本） | KGraph 的多模型隔离与双时态落库更贴合业务                                                   |
| 容错    | 方法级 fallback → 截断减半重试（最小 100 字符）→ 合成 UNKNOWN 实体 → silent\_fail 开关             | JSON 解析失败带原因重试 1 次；校验层 WARNING 不 DROP        | Semantica 更工程化；KGraph 校验墙语义更深                                              |

## 二、抽取深度逐项对比

### 2.1 节点（实体）抽取

| 维度      | Semantica                                                                             | KGraph                                                         |
| ------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 类型体系    | 内置 7 类（PERSON/ORG/GPE/DATE/EVENT/PRODUCT/CONCEPT，OntoNotes 风格），可被用户 `entity_types` 覆盖 | 本体约束注入（type 枚举优先，未命中自定义），事件 type 统一归一为「事件」                     |
| 指代消解    | 独立可选组件 `coreference_resolver`，主链路默认不用                                                 | **内联在阶段1**（coreferenceChains → alias\_map，指代词不建节点，阶段2 引用解析时映射） |
| 事件建模    | EVENT 仅作为实体类型之一，无命名规范                                                                 | 事件 canonicalName 强制「主体+动词+对象完整短语」，语义自包含                        |
| 幻觉防护    | 指令"Extract ONLY from the text"                                                        | 实体表硬约束 + 阶段2 代码 5 级引用解析（精确→别名→包含→Jaccard≥0.80→占位）              |
| span 定位 | LLM 输出文本 + 分块偏移回加                                                                     | mention/canonical 回原文 `find()` 由代码生成 span（LLM 不输出数字偏移，防幻觉数字）   |

**结论**：节点抽取 KGraph 更深——指代消解内联、事件命名规范、span 代码定位都是 Semantica 没有的。

### 2.2 关系抽取（差距最大的一环）

| 维度       | Semantica                                                                                                             | KGraph                                                               | 影响                                                        |
| -------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------- |
| **谓词治理** | **锚点词表**：`related_to / part_of / located_in / created_by / uses / depends_on / interacts_with` + "similar variations" | **零词表 + 鼓励弱连接**：铁律 2 明示"哪怕是「包含于」「关联」「提及」这种弱语义连接也行"                   | KGraph 评估谓词合理性仅 0.60\~0.87，LLM 自由发明「实施/涉及对象/涉原告」等泛化谓词     |
| 实体表注入    | 全量注入但有**上限**：`max_entities_prompt=80`，超出按文本相关性筛选（`filter_entities_for_text`）                                          | 全量注入，无上限                                                             | KGraph 实体一多 prompt 即爆，与切分问题同源                             |
| 证据句      | 无强制                                                                                                                   | **强制**：每条关系必须带 evidenceText，代码 `find()` 校验，定位失败整条丢弃                  | KGraph 显著更优，评估证据句有效性 0.82\~0.93 有此功劳                      |
| 时间有效性    | 扩展版（`extract_temporal_bounds=True`）才有 valid\_from/valid\_until，**8 档置信度标定表 + 5 个 few-shot**                           | 默认全开 vt\_from/vt\_to/vt\_precision + status（CURRENT/EXPIRED/NEGATED） | KGraph 双时态覆盖更全且默认启用（评估 0.92\~1.0）；但 Semantica 的置信度标定表值得借鉴 |
| 分块时的实体过滤 | 每 chunk 只传 span 落在边界 ±100 字符内的实体                                                                                      | 无分块，不适用                                                              | KGraph 做切分时必须实现的机制                                        |

### 2.3 质量校验

| 维度    | Semantica                      | KGraph                                                                                      |
| ----- | ------------------------------ | ------------------------------------------------------------------------------------------- |
| 定位    | `extraction_validator` 为可选辅助组件 | **W1\~W5 校验墙为主链路硬环节**                                                                       |
| 内容    | 基础合法性校验                        | W1 span 合法性 + 证据含 signalWord / W2 时态反序自动交换 / W3 近邻消歧（Jaccard≥0.85）/ W4 因果 DAG 无环 / W5 低置信标记 |
| 置信度过滤 | 抽取器级 `min_confidence` 统一过滤     | W5 仅标记不 DROP（conf<0.60 标 lowConfidence）                                                     |

**结论**：校验墙是 KGraph 的差异化优势，Semantica 没有对等物。

### 2.4 输出 Schema 约束

| 维度        | Semantica                                                                   | KGraph                                                                  |
| --------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 结构保障      | instructor/Pydantic typed generation（`generate_typed`），prompt 无需堆 JSON 修复指令 | DeepSeek `response_format=json_object` + 解析失败带原因重试 1 次 + markdown 代码块兼容 |
| 字段清洗      | Schema 层别名归一（source→subject 等）+ 置信度钳制 \[0,1]                                | 代码校验层逐字段归一（status/type/precision）                                       |
| Prompt 风格 | 极简三段式（骨架 + 类型指令 + 原文），指令仅 3-4 条                                             | 4 条长铁律，用 prompt 下达召回指标（零孤立/密度拉满）                                        |

## 三、评估数据暴露的差距定位

以任务 `2094406639339233282` 的多次评估为证据：

| 指标         | 得分区间                          | 根因归属                                                 |
| ---------- | ----------------------------- | ---------------------------------------------------- |
| 双时态正确性     | 0.92 \~ 1.00                  | prompt 对时间绑定有明确规范 → 表现好                              |
| 实体边界正确性    | 1.00（稳定）                      | 事件命名规范 + 指代消解内联 → 表现好                                |
| 证据句有效性     | 0.82 \~ 0.93                  | 证据句强制回溯机制 → 表现好                                      |
| **谓词合理性**  | **0.60 \~ 0.87（两次评估极差 0.27）** | prompt 无谓词词表 + 鼓励弱连接；泛化谓词（实施/涉及/涉及对象/涉原告）占失分样本 14/25 |
| **三元组忠实度** | **0.61 \~ 0.68**              | 诉讼语料"原告诉称/被告辩称"内容被当平铺事实抽取，schema 无主张归属字段；约 8 条失分源于此  |

**结构性矛盾**：抽取 prompt 的"召回优先"铁律（弱语义连接也行）与评估标准的"精确率要求"（谓词不能宽泛）在同一系统内互相拆台——弱谓词是抽取 prompt 眼里的合规产出，同时是评估 criteria 眼里的扣分项。

**裁判方差**：同一结果两次评估 overall 差 0.1045（0.8956 vs 0.7911），源于推理模型裁判 + 全文注入 + 单次批量判定的非确定性（谓词指标 19 条样本单向降级、0 条升级）。

## 四、KGraph 领先之处（Semantica 不具备）

1. **双时态建模默认全开**：vt\_from/vt\_to/vt\_precision + CURRENT/EXPIRED/NEGATED 四态，Semantica 仅在可选扩展中支持 valid\_from/valid\_until 两字段
2. **指代消解内联主链路**：指代词不建节点、阶段2 自动映射，消除孤立指代节点
3. **证据句强制回溯**：无证据关系直接丢弃，每条知识可定位到原文位置
4. **W1\~W5 确定性校验墙**：span/时态/消歧/DAG/置信五层代码治理，0 次 LLM 调用
5. **Neo4j 多模型隔离 + 关系 CREATE 不 merge**：同名实体多期时态版本共存
6. **事件实体命名规范**：完整动宾短语自包含语义，Agent 检索友好

## 五、Semantica 领先之处（KGraph 待补）

1. **长文本分块流水线**：64K 阈值自动切分 + 10% overlap + 并发抽取 + span 偏移回加 + 分块实体过滤（±100 字符）
2. **谓词锚点词表**：7 个标准谓词 + 允许变体，输出向规范聚集
3. **关系阶段实体表上限**（`max_entities_prompt=80` + 相关性筛选）
4. **置信度标定表**：8 档时间置信度（full ISO=1.0 → 模糊=0.35）+ few-shot，置信度有区分度
5. **截断自适应重试**：`length/max_tokens` 错误时块大小减半重试（最小 100 字符）
6. **独立去重/规范化模块**：抽取与图谱构建解耦

***

## 六、改进路线（按优先级）

### P0 — 消除抽取与评估的自相矛盾（谓词治理）

1. **阶段2 prompt 引入谓词锚点词表**：给出标准谓词集（动作动词优先：拨打电话/寄送/起诉/受理/审理/发布/担任/位于/隶属…），允许"similar variations"；**删除"弱语义连接也行"的表述**
2. **强弱边分层**：确需弱连接防孤立时，限定使用封闭弱谓词集（关联/提及/涉及），并打 `confidence ≤ 0.5` 标记；评估侧对弱边只判"该不该弱连"，不按精确率标准惩罚
3. **W6 校验**：谓词命中泛化黑名单（实施/涉及对象/相关/有关）→ confidence 降档 + 标记 weak edge

### P1 — 事实性归属维度

1. **schema 增加** **`attribution`** **字段**（原文直述/原告主张/被告主张/权威认定）：解决"诉称内容当事实抽"的忠实度失分；评估忠实度对主张类关系只查"原文是否确实有此主张"

### P2 — 长文档流水线（对标 Semantica）

1. **结构优先切分**：Markdown 标题层级一级切分（1000\~3000 字），超长小节内部滑窗兜底（\~2000 字 + 200 重叠）
2. **分块并发 + span 回加**：chunk 偏移量加回实体/证据 span
3. **分块实体过滤**：每 chunk 只注入 span 落在边界 ±100 字符内的实体（复刻 Semantica 设计）
4. **关系阶段实体表上限**：超过 80 个实体按文本相关性筛选
5. **聚合层**：跨块实体按 canonicalName 合并、指代链二次消解、统一走 W1\~W5 后写入

### P3 — 置信度标定

1. **confidence 标定表**：参照 Semantica 8 档设计（明确时间锚点=高 / 间接推断=低），使 confidence 成为可信的过滤与评估信号

***

## 七、一句话总结

> KGraph 赢在语义深度（双时态、指代消解、证据回溯、校验墙），Semantica 赢在流水线工程（分块、并发、去重、谓词锚点、置信度标定）。
> 当前评估失分（谓词/忠实度）不是 LLM 能力问题，而是 prompt 治理缺失与 schema 维度缺失；长文档不可用则是流水线工程环的缺位。
> 补齐谓词锚点词表 + attribution 字段 + 切分聚合链路后，两条路线的优势即合并完成。

## 八、实测对比实验记录（8002 对比台）

> 实验环境：`pybackend/semantica_ext/`（8002 独立服务，WarSee conda 环境），KGraph 走 8001 `dryRun` 模式（不写 Neo4j）。
> 公平性控制：同一语料 + 同一抽取模型（deepseek-chat）+ 同一裁判模型（deepseek-chat，非推理模型方差小）+ 同一评估标准（8001 五裁判指标）。
> 原始数据：[compare_sanguo1000_chat_20260911.json](./实验数据/compare_sanguo1000_chat_20260911.json)

### 实验 1：三国-1000字-小语料（2026-09-11）

| 维度 | KGraph | Semantica | 差异 |
|---|---|---|---|
| 实体数 | **111** | 81 | KGraph +37%（指代消解归并更多 mention + 事件实体规范） |
| 关系数 | **92** | 81 | KGraph +14% |
| 带证据关系 | 92/92（100%） | 81/81（100%）* | *Semantica 证据为适配层从 context 切句回原文定位 |
| 抽取耗时 | 33s | 35s | 相当 |
| **内在指标** | | | |
| 孤立实体率 | 27.9% | 29.6% | 相当（均偏高，W3.6 补边后为 0） |
| 证据覆盖率 | 90.2% | 100%* | *Semantica 适配层切句即证据，口径不同 |
| **LLM 裁判指标** | | | |
| 三元组忠实度 | 0.9239 | 0.9198 | 持平 |
| 谓词合理性 | **0.8370** | 0.7901 | KGraph +6%（弱谓词治理初见效） |
| 双时态正确性 | **0.9946** | 0.9753 | KGraph +2%（9 档置信度标定） |
| **证据句有效性** | **0.8913** | 0.4198 | **KGraph +112%（核心差距）** |
| 实体边界正确性 | 0.9730 | 0.9815 | 持平（Semantica 略优） |
| **综合（5 裁判均值）** | **0.9240** | **0.8173** | **KGraph +13%** |

### 实验 1 结论

1. **证据句有效性是最大差距（0.89 vs 0.42）**：Semantica 的 `context` 是 LLM 返回的"上下文片段"（常为大段原文或改写），无精确证据回溯机制；KGraph 阶段 2 强制 `evidenceText` + 代码回原文 `find()` 定位，证据句干净精确。验证了第二章"关系抽取差距"的分析。
2. **谓词合理性 KGraph 领先 6%**：P0 谓词治理（标准谓词优先 + 弱谓词兜底 conf≤0.5 分层）的效果体现；Semantica 的谓词锚点词表优势（第五章）并未在其默认 LLM 链路中生效。
3. **实体量差 37%**：KGraph 指代消解（coreferenceChains 归并 aliases 不丢 mention）+ 事件实体完整短语规范，产出更完整的实体表；Semantica 主链路默认不启用 coreference_resolver。
4. **双时态 KGraph 略优**：两者都能抽（Semantica 走 `extract_temporal_bounds` 扩展），但 KGraph 的 9 档时间信号强度标定使 vt 精度判定更稳。
5. **成本相当**（33s vs 35s）：Semantica typed 模式 + FastEmbed 失败回退未显著拖慢小语料。

### 已知实验局限

- 单语料单次运行，未做多次重复的方差检验（后续同配置跑 3 次取均值）
- Semantica 证据句经适配层加工（非原生证据），其 0.42 分含"context 与三元组关联松散"的框架固有因素——属公平呈现框架差异，但数值受适配策略影响
- Semantica token 消耗未计入（provider 不返回 usage）
- 抽取质量管道（W1-W5）只作用于 KGraph 侧，Semantica 无对应校验墙——反映两框架设计哲学差异（工程深挖 vs 流水线通用）
