# 语料分块功能设计方案 —— 技术文档

> 版本：v1.0（2026-09-06） | 适用模块：语料管理 → 操作栏「分块」 | 定位：P2 长文档抽取流水线的前置基础设施（本期仅做分块计算与存储，抽取侧零改动）

---

## 0. 边界声明（严格遵守）

1. **本期只实现「分块计算 + 结果入库 + 前端查看」**，LLM/KOS/DL/结构化四条抽取链路 **零代码改动**；分块结果暂不参与任何抽取流程。
2. Python 端 `/api/split` 为 **无状态纯函数接口**：只接收文本与策略参数，不感知 corpusId / 用户 / 数据库——保证未来抽取流水线可复用同一分块器。
3. 不引入外部依赖（langchain text_splitter 等），分块算法全部自实现；现有 `text_processor/splitter.py`（DL 训练管线在用）**不动**，其算法吸收为 `fixed` 策略后未来再合并。
4. 语义分块（embedding 相似度切分）**本期不做**，列入远期扩展——需要向量模型推理，成本与收益不匹配。
5. 分块为 **同步调用**：纯 CPU 文本处理，常规语料毫秒级、10MB 极端语料 1~2s，无需异步任务化。

---

## 1. 背景与定位

- **直接动因**：语料管理操作栏增加「分块」入口，用户可对单篇语料按策略切分并查看结果。
- **战略定位**：对比文档（KGraph vs Semantica）P2 路线指出当前抽取整篇读取语料（`ExtractionTaskServiceImpl` 直接 `corpus.getContent()`），长文档不可用。`corpus_chunk` 表是未来「按块抽取 + span 偏移回加 + 跨块实体合并」流水线的地基，**本期把地基打对（尤其偏移量语义），流水线后建**。

---

## 2. 总体架构

```
前端 Corpus.vue 操作栏「分块」
    │ POST /corpus/{id}/chunks {strategy, chunkSize?, overlap?}
    ▼
Java CorpusController（鉴权 + 项目隔离）
    │ 1. 读 corpus.content，校验 status=已完成
    │ 2. PythonServiceClient.splitText(text, strategy, params)
    ▼
Python POST /api/split（无状态纯函数）
    │ splitter 包按策略计算 → 参数钳制 → 块数上限保护
    ▼ 返回 chunks: [{index, content, startOffset, endOffset, charCount}]
Java CorpusChunkService（事务）
    │ delete 旧块（覆盖式重建）→ batch insert 新块
    ▼ 返回 {strategy, totalChunks, avgCharCount, duration}
前端：分块查看抽屉（统计条 + 块列表分页 + 偏移区间展示）
```

**职责分工**（与现有架构一致）：Python = 算法（无状态）、Java = 业务 + 持久化 + 鉴权、前端 = 交互。

## 3. 数据库设计

新建表 `corpus_chunk`（当前 `corpus` 表之外无任何分块存储，需新建）：

```sql
CREATE TABLE IF NOT EXISTS corpus_chunk (
    id           BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '主键ID',
    corpusId     BIGINT        NOT NULL COMMENT '所属语料ID',
    projectId    BIGINT        NOT NULL COMMENT '所属项目ID（冗余，便于按项目统计）',
    chunkIndex   INT           NOT NULL COMMENT '块序号，从0开始',
    content      MEDIUMTEXT    NOT NULL COMMENT '块文本',
    startOffset  INT           NOT NULL COMMENT '块起始偏移（闭区间，含）',
    endOffset    INT           NOT NULL COMMENT '块结束偏移（闭区间，含）',
    charCount    INT           NOT NULL COMMENT '块字符数',
    strategy     VARCHAR(32)   NOT NULL COMMENT '分块策略: fixed/sentence/recursive/structure',
    chunkSize    INT           COMMENT '生成时的块大小参数（快照）',
    overlap      INT           COMMENT '生成时的重叠参数（快照）',
    createBy     BIGINT        COMMENT '操作人ID',
    createTime   DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    isDeleted    TINYINT(1) DEFAULT 0 COMMENT '逻辑删除',
    UNIQUE KEY uk_corpus_chunk (corpusId, chunkIndex),
    INDEX idx_projectId (projectId)
) COMMENT '语料分块表' COLLATE = utf8mb4_unicode_ci;
```

**关键设计点**：

| 设计 | 说明 |
|---|---|
| **偏移量必存** | P2 按块抽取时，实体/证据 span 需 + chunk.startOffset 才是全局位置（对齐 Semantica 分块偏移回加机制）。没有 offset，此表对流水线无价值 |
| **闭区间语义** | `startOffset` 含、`endOffset` 含，切片语义 `text[start : end+1]`——与抽取侧 `EvidenceSpan` 闭区间惯例**全系统统一**，避免换算出错 |
| **参数快照** | 每行冗余 strategy/chunkSize/overlap，重新分块整表覆盖，无需版本管理 |
| **覆盖式重建** | 重新分块 = 事务内 delete 该 corpusId 全部旧块 + insert 新块；UNIQUE KEY 兜底防重复 |
| **charCount** | 冗余存储，前端列表直接展示，避免 content 全量拉取 |

## 4. Python 端设计

### 4.1 包结构

```
pybackend/splitter/
  __init__.py     # 注册表 STRATEGY_REGISTRY: 名称 → 策略类
  base.py         # Chunk 数据类 + SplitStrategy 抽象基类
  fixed.py        # fixed：固定长度滑窗（吸收 text_processor/splitter.py 算法）
  sentence.py     # sentence：句子感知合并
  recursive.py    # recursive：递归字符分割（分隔符层级降级）
  structure.py    # structure：结构优先（标题切节 + 滑窗兜底）

pybackend/api/splitter.py   # POST /api/split 路由，main.py 注册
pybackend/test/test_splitter.py  # 4 策略单测
```

### 4.2 数据契约

```python
# base.py
class Chunk(BaseModel):
    index: int          # 块序号，0-based
    content: str        # 块文本（strip 后）
    startOffset: int    # 闭区间起点（strip 前定位，strip 后重算）
    endOffset: int      # 闭区间终点
    charCount: int      # = len(content)

class SplitStrategy(ABC):
    name: str
    default_size: int
    default_overlap: int
    @abstractmethod
    def split(self, text: str, chunk_size: int, overlap: int,
              separator: str | None = None) -> List[Chunk]: ...
    # separator 仅 recursive 策略消费（用户自定义一级分隔符，默认 "\n\n"），
    # 其余策略忽略该参数，保证统一签名
```

> 偏移量语义细节：块内容 strip 前后偏移会漂移，实现时以 **strip 后内容在原文中的真实位置** 为准（`text.find` 定位或边切边记），禁止先切后统一重算导致重叠块偏移错位。

### 4.3 四种策略算法

| 策略 | 算法 | 默认参数 | 适用 |
|---|---|---|---|
| **fixed** 固定长度滑窗 | 步长 = size − overlap 滑窗；每窗内优先回找句末边界（。！？!? 后跟空白/换行，且命中位置 > 窗长 30%）截断，找不到硬切 | 1000 / 100 | 通用兜底，行为最可预期 |
| **sentence** 句子感知 | 正则按句末标点（。！？!?；;）+ 换行切段，保留分隔符；贪心合并相邻段至 size 上限；单段超 size 降级硬切；overlap 从上块尾部回取 ≤ overlap 的完整句 | 1000 / 100 | 保持句子完整，LLM 抽取友好 |
| **recursive** 递归字符 | 分隔符层级 `["\n\n", "\n", "。", "！", "？", "；", "，", " "]` 逐级降级：先按段落切，段 ≤ size 直接收，超长段用下一级分隔符再切；相邻碎块贪心合并至 size；overlap 尾部回补。**一级分隔符可由用户自定义**（默认 `\n\n`，替换层级首元素） | 1000 / 100 | langchain 经典方案，中文优先标点 |
| **structure** 结构优先 | 识别标题（Markdown `#` 系列 + 中文编号「一、/（一）/1./1.1」）；按标题切节，标题保留在所属块首；单节 ≤ size 成一块，超长节内部用 fixed 滑窗兜底（仅首块含标题，兜底块不带前缀以保偏移真实）；全文无标题 → 整体降级 recursive | 2000 / 200 | MinerU 解析的结构化文档；P2 抽取的目标策略 |

### 4.4 API 定义

```
POST /api/split
Request:  { "text": str, "strategy": str, "chunkSize"?: int,
            "overlap"?: int, "separator"?: str }
Response: { "strategy", "chunkSize", "overlap", "separator", "totalChunks",
            "chunks": [{"index", "content", "startOffset", "endOffset", "charCount"}] }
```

**参数钳制与保护**（防误用/防爆）：

| 参数 | 约束 | 违规处理 |
|---|---|---|
| text | 非空，≤ 10MB | 空 → 400；超限 → 413 |
| strategy | ∈ {fixed, sentence, recursive, structure} | 非法 → 400 |
| chunkSize | [100, 8000]，缺省取策略默认 | 越界钳制到边界值（不报错） |
| overlap | [0, chunkSize/2]，缺省取策略默认 | 越界钳制 |
| separator | 仅 recursive 消费；非空、≤ 20 字符；`\n`/`\t` 转义还原 | 空 → 用默认；超长 → 400 |
| 块数 | ≤ 2000 | 超出 → 422（提示调大 chunkSize） |

## 5. Java 端设计

### 5.1 接口（CorpusController 新增 4 个）

| 接口 | 说明 |
|---|---|
| `POST /corpus/{id}/chunks/preview` | **分块预览（dry-run，不落库）**。Body 同执行接口 `{strategy, chunkSize?, overlap?, separator?}`；读语料内容调 Python 计算，仅返回统计 + 前 10 块：`{strategy, totalChunks, avgCharCount, previewChunks[10]}`。供前端对话框内实时预览，参数可反复调整重试 |
| `POST /corpus/{id}/chunks` | 执行分块落库。Body: `{strategy, chunkSize?, overlap?, separator?}`；前置校验：语料存在 + status=1（已完成）+ 归属当前用户项目；调 Python → 事务内删旧插新；返回 `{strategy, totalChunks, avgCharCount, duration}` |
| `GET /corpus/{id}/chunks?pageNum&pageSize` | 分页查看块列表（id/chunkIndex/startOffset/endOffset/charCount/content），默认 pageSize=20 |
| `DELETE /corpus/{id}/chunks` | 清空该语料全部分块 |

**列表接口改造**：`GET /corpus/list` 每行补充 `chunkCount`（子查询 COUNT，分页 10 条开销可忽略）——前端据此判断「点击分块 → 弹对话框（无块）还是开抽屉（有块）」。

### 5.2 组件清单

```
model/entity/CorpusChunk.java            # 实体
mapper/CorpusChunkMapper.java            # 含 deleteByCorpusId（物理删，分块可随时重建）
service/CorpusChunkService(+Impl).java   # chunkCorpus / previewChunks / pageChunks / clearChunks
config/PythonServiceClient.java          # 新增 splitText(text, strategy, size, overlap, separator)
```

### 5.3 一致性维护（分块失效处理）

| 场景 | 处理 |
|---|---|
| **语料内容被编辑** | `CorpusServiceImpl.update` 保存新内容时，事务内物理删除该语料全部分块，接口返回 `chunkReset: true`；前端提示「内容已更新，原有分块已清除，请重新分块」 |
| **语料被删除** | `CorpusServiceImpl.delete` 事务内级联清空分块 |
| **重新分块** | 覆盖式重建（见 3 节），同一时刻每语料仅存一套分块结果 |

> 选择「自动清空 + 提示」而非「保留并标失效」：分块是纯计算产物，可随时低成本重建，保留脏数据只有维护成本没有收益。

**预览机制**（对应 5.1 dry-run 接口）：

- 点击「预览分块效果」→ 按钮 loading → 调 `POST /corpus/{id}/chunks/preview` → 右栏渲染统计行（总块数/平均块长）+ 前 10 块卡片（序号/字符数/偏移区间/内容 3 行截断可展开）；
- **任何参数变更后**，右栏底部显示灰色提示条「参数已变更，预览结果可能过期」，引导重新预览；
- 预览失败（422 块数超限等）：右栏原位显示错误卡片（含后端原因），不弹全局消息；
- 允许不预览直接「执行分块」（预览非强制，对短语料可跳过）。

**执行分块**：按钮 loading → 成功关闭对话框 → 自动打开分块结果抽屉；已有分块时对话框顶部显示 el-alert：「该语料已有 N 块分块结果，本次执行将覆盖重建」。

## 7. 异常与边界场景

| 场景 | 行为 |
|---|---|
| Python 服务不可用 | POST 分块返回 503，提示「分块服务暂不可用」，语料本身不受影响 |
| 超长语料（接近 MEDIUMTEXT 16MB） | Python 侧 10MB 上限拦截 413；提示拆分语料 |
| 空白文本 / 无有效内容 | chunks 返回空数组，Java 侧拒绝入库并提示 |
| 并发对同一语料分块 | 事务 + UNIQUE KEY 兜底；后写覆盖先写，无脏数据 |
| 4 种策略对同一语料结果差异大 | 属预期，抽屉顶部策略徽标明确当前生效策略 |
